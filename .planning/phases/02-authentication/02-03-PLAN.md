preValidation hook pattern (from RESEARCH.md Pattern 4):
```typescript
// Scoped to WS plugin only — does NOT affect /health or /auth/* routes
fastify.addHook('preValidation', async (request, reply) => {
  await fastify.authenticate(request, reply);
});
```

Hook timing (critical — from RESEARCH.md Pitfall D):
- Use preValidation (NOT onRequest) — @fastify/cookie runs in onRequest, populating request.cookies
- preValidation fires AFTER cookies are parsed, so access_token cookie is available
- reply.code(401).send() in preValidation aborts the request BEFORE the WebSocket upgrade is accepted
- No socket is allocated on 401 — clean rejection (PITFALLS.md #3 prevention)

    import fp from 'fastify-plugin';
    import type { FastifyInstance } from 'fastify';

    export default fp(async (fastify: FastifyInstance) => {
      // preValidation hook scoped to this plugin only.
      // Fires after @fastify/cookie (onRequest) has parsed cookies.
      // reply.code(401).send() here rejects the HTTP upgrade request —
      // no WebSocket connection is allocated (PITFALLS.md #3).
      // Do NOT use a global hook — /health and /auth/* must remain unprotected.
      fastify.addHook('preValidation', async (request, reply) => {
        // Only enforce on WebSocket upgrade requests to this plugin's routes
        await fastify.authenticate(request, reply);
      });

      fastify.get('/ws', { websocket: true }, (socket, request) => {
        const userId = request.user.sub;

        fastify.log.info({ userId }, 'WebSocket connection established');

        // Placeholder handlers — Phase 3 will implement full message routing
        socket.on('message', (data) => {
          // Echo for smoke-testing auth; Phase 3 replaces this
          socket.send(JSON.stringify({ type: 'connected', userId }));
        });

        socket.on('close', () => {
          fastify.log.info({ userId }, 'WebSocket connection closed');
        });

        socket.on('error', (err) => {
          fastify.log.error({ userId, err }, 'WebSocket error');
        });
      });
    });

    **IMPORTANT:** The preValidation hook inside the ws plugin is scoped to that plugin only because it uses `fp` (fastify-plugin) which by default does NOT break encapsulation for hooks — actually, `fp` DOES break encapsulation for decorators and plugins but hooks added with `addHook` inside fp-wrapped plugins ARE scoped. Wait — this is subtle:

    In Fastify, `addHook` inside a plugin scope adds the hook only to that scope and its children. When wrapped with `fp` (fastify-plugin), the plugin runs in the parent scope, so `addHook` inside it would affect the parent scope globally.

    To properly scope the hook to only the /ws route, do NOT wrap the ws plugin with `fp`. Instead, use a non-fp plugin so it gets its own encapsulated scope:

    ```typescript
    // server/src/routes/ws/index.ts
    // NOT wrapped with fp — gets its own scope so preValidation hook is scoped here
    import type { FastifyInstance } from 'fastify';

    export default async function wsRoutes(fastify: FastifyInstance): Promise<void> {
      fastify.addHook('preValidation', async (request, reply) => {
        await fastify.authenticate(request, reply);
      });

      fastify.get('/ws', { websocket: true }, (socket, request) => {
        // ...same as above
      });
    }
    ```

    Using a plain async function export (not fp-wrapped) keeps this plugin in its own Fastify scope. The `authenticate` decorator is still accessible because it was registered with `fp` in auth.ts — fp breaks encapsulation for decorators (they bubble up). So `fastify.authenticate` is available here even without fp on this plugin.
